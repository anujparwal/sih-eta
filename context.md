# Project Overview

RailScope is a student prototype for **SIH26028 — Dynamic Forecast of Expected Time of Arrival (ETA) for Coaching Trains**. The repository is <https://github.com/anujparwal/sih-eta>.

The aim is to help passengers understand train arrivals while demonstrating an explainable next-station ETA model that responds to changing conditions. The current priority is the public passenger experience, truthful data provenance and a credible SIH demonstration. The team has requested zero-cost operation; paid cloud resources have not been provisioned.

**Three distinct experiences exist:**

1. **Public passenger lookup:** real RailRadar provider reports for a requested five-digit train number, origin departure date and destination. Availability and freshness depend on the provider. These reports are not generated by our model.
2. **Synthetic railway demonstration:** six trains on attributed historical Indian routes, with simulated movement/incidents, baseline estimates, XGBoost predictions and TreeSHAP explanations.
3. **Experiment lab:** hypothetical inputs applied to the reviewed synthetic model, with baseline comparisons, explanations, explicit fallbacks and evaluation evidence.

Never present synthetic results as real railway accuracy, provider estimates as independently observed arrivals, or the deployed fixed model as automatically self-learning.

**Memory snapshot:** 9 October 2026, Asia/Kolkata. This document combines the user's conversation requests with repository inspection and local verification. Conversation history establishes intent and permissions; code, tests and checked-in evidence establish implementation status.

# Architecture & File Structure

## Runtime design

**Provider path:** browser → Next.js GET proxy → FastAPI `railradar.py` → fixed RailRadar HTTPS upstream. Redis coordinates caching, coalescing, cooldowns and call budgets. Provider data stays separate from synthetic SQL telemetry and ML features.

**Simulation path:** sourced network fixture → idempotent PostGIS seed → one Python simulator → validated HTTP ingestion → PostgreSQL commit → Redis invalidation/publication → FastAPI REST/WebSocket snapshots → Next.js dashboards. REST and WebSocket predictions share one calculation path.

**Lab path:** browser form → `GET /demo/scenario` → reviewed artifact plus shared feature/model rules → baseline, hypothetical prediction, attribution and evidence. No provider calls, telemetry writes or training occur here.

**Offline ML path:** reproducible synthetic complete journeys → shared serving feature arithmetic → chronological whole-journey train/validation/test splits → validation-selected XGBoost → reviewed JSON model and metadata → backend image. Startup loads, rather than trains, the model.

Database tables include `stations` (SRID 4326 POINT/GiST), `routes` (schematic LINESTRING), `route_stops` (ordered distances and unwrapped IST timetable offsets), `live_positions`, `events` and `historical_delays`. Telemetry timestamps are timezone-aware UTC. Journey anchors preserve multi-day schedule semantics. Historical delay aggregates start empty; no invented history is seeded. Unversioned aggregates are excluded from the training vector to avoid future-data leakage.

### Public passenger functionality

- `/` and `/live` accept a five-digit train number and origin date; a blank date defaults to the current IST date. Results are fetched only on user action, without automatic provider polling.
- Normalized results include train status, provider/fetch timestamps, stop timings, platform information where supplied and route geometry/coordinates where available.
- A destination card compares reported and scheduled arrivals using complete IST dates. Repeated station visits retain exact stop identity. Labels remain readable without exposing raw fractional sequence identifiers.
- Journey links preserve train, origin date and stop occurrence. Opening a link does not automatically spend a provider request. Clipboard failure exposes a selectable link.
- Editing lookup inputs cancels pending work and clears old results. Loading, missing, stale and upstream failure states are explicit.
- Countdown eligibility requires a fresh live running report, an upcoming confirmed halt and a future reported arrival. Stale, unknown, skipped, cancelled, passed or otherwise unsupported cases withhold the countdown.
- Provider freshness uses report time, not fetch time: recent reports are within ten minutes; implausibly future-dated reports become unknown. Displayed age continues updating while the page is open.
- The map uses supplied geometry only. A reported station is distinguished from an explicitly supplied train position. No guessed track path or animated extrapolated position is presented as live evidence.
- Shared provider controls include a five-minute cache, up-to-24-hour fallback, lock/coalescing, one-minute cooldown and daily/monthly attempt budgets. Failed upstream calls consume budget. Redis failure fails closed.
- Fixed upstream host, rejected redirects, bounded responses, sanitized errors and train/date mismatch checks protect the integration. API credentials remain backend-only.

### Simulation, model and dashboards

- The historical fixture contains **six routes, 63 stations and 91 route stops**. Train numbers: `12301`, `12621`, `12622`, `12627`, `12952`, `12953`.
- One simulator emits approximately five-second samples, realistic progression/dwell and synthetic disruptions/occupancy. Restart/completion creates new journey IDs; occupancy and route connectors are approximations.
- Ingestion validates route, ordering, coordinates and finite values. UUID retries are idempotent. SQL commits precede Redis publication; retrying the same UUID/body repairs a post-commit delivery failure without duplicate rows.
- Shared ingestion limits default to 120 requests/minute per socket peer with a 16 KiB body limit. Proxy headers are not trusted as peer identity.
- Redis supports cross-process notifications and cached fleet aggregation. WebSockets send initial/reconnected state, reconcile missed notifications every 15 seconds and expose stale observations after 30 seconds.
- `/demo` shows simulated train movement and next-station ML/baseline comparisons. `/station/[code]` refreshes arrivals every ten seconds. `/control` provides fleet sorting/filtering, timelines, journey history and events.
- The independent baseline carries current delay forward. XGBoost predicts the next-station residual; native TreeSHAP explains it. Downstream stations retain the baseline. Missing, incompatible or unsupported inputs/artifacts explicitly fall back.
- `/lab` demonstrates quiet, severe-disruption and unsupported-congestion scenarios, signed feature contributions, reviewed evaluation metadata and downloadable JSON evidence. It clearly labels hypothetical inputs and synthetic training.

# Known Issues & Blockers

No unresolved application compilation failure or failing test was found by the checks above. That establishes tested behavior, not a guarantee of zero defects.

- **Public hosting is not deployed.** Render/Vercel configuration exists, but the checked-in Render resources include paid plans and do not satisfy the team's zero-rupee requirement. No public service URL or production SLA exists.
- **Provider availability is external.** On-demand lookup can request arbitrary train numbers, but continuous 24/7 coverage, fresh reports for every running train and correctness cannot be guaranteed. Local 30/day and 900/month budgets are not a claim about the current provider plan or remaining account quota.
- **Real-world ML validation is missing.** The model is synthetic-trained. RailRadar integration does not supply model training inputs or verified arrival labels. Provider fields named `actualArrival`/`actualDeparture` are normalized as reported times because they can contain estimates.
- **No automatic self-learning exists.** `ml/refresh_history.py` is a manual, dry-run-default aggregation tool; no automatic retraining, model promotion or online adaptation is running.
- **Prototype operational limits remain.** Read APIs are public; there are no accounts/roles or comprehensive public abuse controls. Redis pub/sub has no durable replay/outbox. Cache expiry and reconciliation recover current state, but this is not durable event delivery.
- **Data/scale limits remain.** Historical timetable data and schematic geometry are not current surveyed railway infrastructure. Long-term retention, production load/cost, monitoring and recovery have not been validated at national scale.
- **Submission/publishing remains external.** No YouTube upload or SIH portal submission was performed. The portal screenshot warned that edits were available once and showed an October 5 deadline; its current availability has not been verified. Do not submit or overwrite the application based on this memory alone.

The earlier SIH title used “Self-Learning.” Prefer wording such as **“RailScope: Explainable Dynamic ETA Forecasting for Coaching Trains”** unless self-learning is clearly described as future work. Do not include blockchain as an implemented technology.
